# Bluetooth Replacement Plan

## 1. 目标

本方案用于在 `BT_Version` 分支上评估并规划“使用蓝牙替代当前 ESP32 <-> AI8051U I2C 通信链路”的可行实现。

约束条件如下：

- 保留当前稳定版的动作对象、LED 预设、调试菜单、截图链路和 MCP 工具能力。
- 尽量复用现有 `gp_led_matrix_protocol` 包格式，不重写上层业务协议。
- AI8051U 保持现有 WS2812 渲染和动作执行架构，不在 8051 侧引入重型蓝牙协议栈。
- 当前验证目标板为 `lichuang-dev (ESP32-S3)`；本次在 `ESP-IDF v5.4.3` 下实测尝试接入经典蓝牙 SPP 后，链接阶段缺少 `esp_spp_* / esp_bt_gap_*` 符号，因而该目标下不能形成可运行的经典蓝牙 SPP 固件。
- `BT_Version` 当前已先行实现 AI8051U 侧 `UART2 + HC-05` 接口，并完全关闭了 AI8051U 的矩阵链路 I2C 初始化。

## 1.1 当前分支结论

- AI8051U `UART2(P4.2/P4.3)` 对接 `HC-05` 的串口透明传输路径可以实现，当前分支已按该方向改造 8051 驱动。
- ESP32 侧已新增矩阵传输抽象层，并实现了条件编译的经典蓝牙 SPP 传输后端；该后端仅适用于具备经典蓝牙能力且能完成链接的目标芯片。
- 若保持 `lichuang-dev` 不变，则当前可运行方案仍是 I2C 或改用 BLE 串口模块；若保持 `HC-05` 不变，则需要改用支持经典蓝牙并能链接 SPP API 的 ESP32 目标芯片。

## 2. 推荐总体方案

在当前硬件约束下，推荐采用“ESP32-S3 BLE GATT Client + AI8051U 外挂 BLE 串口透传模块”的双层结构：

1. ESP32 侧：
   - 新增 BLE 传输适配层，负责扫描、配对、建链、分片发送、通知接收和重连。
   - 上层仍复用现有 `GpMatrixActionPayload`、`gp_led_matrix_protocol` 和链路状态摘要逻辑。
2. AI8051U 侧：
   - 通过 UART 与 BLE 模块通信。
   - 将 BLE 模块透传的串口数据送入现有协议解析器。
   - 执行结果通过 UART 回发给 BLE 模块，再由模块透传给 ESP32。
3. BLE 模块：
   - 选择支持 BLE 透传的模块，优先要求支持可配置 MTU、稳定通知、低功耗广播和透明串口模式。

该方案的核心思想是：

- 用 BLE 替换当前 I2C 物理层。
- 用 UART 替代 AI8051U 侧与外部无线模块的硬件接口。
- 尽量保持应用协议不变，只新增 BLE 分包、重传和连接管理。

## 3. 为什么当前板型不能落地经典蓝牙 SPP

当前在 `ESP-IDF v5.4.3` 下对 `lichuang-dev (ESP32-S3)` 做了实际接入验证。结果是：头文件和配置项可以写入，但最终链接阶段缺少 `esp_spp_*` 和 `esp_bt_gap_*` 符号，因此不能形成可运行映像。

因此，当前板型若坚持无线链路，仍应优先采用 BLE：

- ESP32 侧实现 BLE GATT Client。
- 外挂模块暴露自定义服务或兼容 NUS 风格服务。
- 数据以 characteristic write/notify 方式传输。

## 4. 硬件改造建议

### 4.1 ESP32 侧

- 保持当前 `lichuang-dev` 硬件主体不变。
- 移除或停用原有 AI8051U I2C 对接路径。
- 保留现有电源、调试串口、屏幕、触摸和网络链路。

### 4.2 AI8051U 侧

- 新增一块 BLE 透明串口模块。
- AI8051U 与 BLE 模块通过 UART 连接。
- 建议额外预留 1 个状态引脚，用于连接成功/失联状态检测。

推荐连接信号：

- `AI8051U TX -> BLE_RX`
- `AI8051U RX -> BLE_TX`
- `BLE_STATE -> AI8051U GPIO 输入`
- `3.3V/GND` 统一供电

### 4.3 模块选择要求

- 对 `lichuang-dev`，必须支持 BLE，或改用其他可实际支持经典蓝牙 SPP 的主控目标。
- 必须支持稳定的串口透传或可预测的 GATT 数据收发。
- 必须支持主从角色中与 ESP32-S3 配套的连接模式。
- 需要明确最大单包长度、广播内容、服务 UUID 和通知行为。

## 5. 软件架构调整

### 5.1 ESP32 侧新增层次

建议新增 `gp_led_matrix_ble_transport` 层：

- 扫描目标 BLE 模块。
- 连接并发现 GATT 服务。
- 对 TX characteristic 做 write。
- 对 RX characteristic 开启 notify。
- 将收到的字节流重组为完整协议包。
- 向上提供与 I2C 版本相同的“发命令/收回包”接口。

建议分层：

1. `BleLinkManager`
   - 扫描、连接、断链重连、MTU 协商。
2. `BlePacketChannel`
   - 分片发送、分片拼包、缓冲管理。
3. `GpLedMatrixBleEsp32`
   - 对齐当前 `GpLedMatrixEsp32` 的命令语义和状态文本输出。

### 5.2 AI8051U 侧改造方向

建议新增 UART 接收前端，而不是改写现有动作执行层：

- UART ISR 或 DMA 接收 BLE 模块透传字节流。
- 在包边界完整后进入现有 `gp_led_matrix_ai8051u` 风格解析路径。
- 生成 ACK/状态回包后，通过 UART 发回 BLE 模块。

可以保留当前协议层的以下资产：

- 魔数、版本号、命令字、序号、长度、校验。
- `SetAction`、`FrameChunk`、`Heartbeat` 等命令语义。
- 状态码定义和错误回包格式。

## 6. 协议迁移策略

### 6.1 保留不变的部分

- `gp_led_matrix_protocol.h` 的包结构。
- 现有动作对象到协议 payload 的映射。
- AI8051U 侧执行结果和状态码语义。

### 6.2 新增的 BLE 传输约束

由于 BLE characteristic 单次 write/notify 有长度限制，需要新增传输层规则：

1. 应用协议包仍然按原始格式构造。
2. BLE 发送层按 MTU 大小切片。
3. 接收端按顺序拼接，直到得到完整协议包。
4. 若超时未收齐整包，则丢弃本次组包并记错误计数。

建议增加一个轻量传输头，仅用于 BLE 分片层，不改动应用协议主体：

```text
| BLE_CH | session_id | frag_index | frag_count | payload... |
```

说明：

- `session_id` 用于区分并发或重发轮次。
- `frag_index/frag_count` 用于拼包。
- `payload` 承载原始 `gp_led_matrix_protocol` 字节流片段。

## 7. 连接与状态机设计

### 7.1 ESP32 侧

建议状态机：

- `IDLE`
- `SCANNING`
- `CONNECTING`
- `DISCOVERING`
- `ONLINE`
- `RECONNECT_WAIT`
- `ERROR`

进入 `ONLINE` 后才允许发送矩阵控制命令。

### 7.2 AI8051U 侧

建议状态机：

- `OFFLINE`
- `BLE_WAIT_LINK`
- `BLE_ONLINE`
- `PACKET_RX`
- `PACKET_READY`
- `REPLY_TX`

当 `BLE_STATE` 或串口链路超时异常时，自动回到 `BLE_WAIT_LINK`。

## 8. ACK 与时序策略

I2C 版本当前带有较强的同步读回语义，而 BLE 更适合异步收发，因此建议这样调整：

1. ESP32 发命令时保留 `sequence`。
2. AI8051U 在执行前先快速返回 ACK 或 `accepted` 状态。
3. 若需要结果状态，可再通过通知返回 `done` 或 `error`。
4. ESP32 侧将原“立即读回”逻辑改为“等待对应 sequence 的通知回包”。

建议超时分层：

- 建链超时
- 单包拼接超时
- ACK 等待超时
- 结果等待超时

## 9. 性能预估与边界

蓝牙版本相对 I2C 版本的主要变化：

- 延迟增大。
- 抖动增大。
- 吞吐受 MTU、连接间隔和 notify 速率影响更明显。
- 但布线约束减小，物理部署更灵活。

因此蓝牙版本建议优先支持：

- `SetAction` 类短包命令。
- 预设、纯色、亮度、模式切换。
- 心跳、状态回读。

不建议一开始就把高频大帧流作为主要目标。

## 10. 迁移步骤建议

### 阶段 1：硬件打样

- 选定 BLE 模块。
- 完成 AI8051U UART 与模块连接。
- 完成 ESP32-S3 与模块的扫描、连接和最小收发验证。

### 阶段 2：透传链路打通

- ESP32 发送固定测试字符串。
- AI8051U 接收并回显。
- 验证重连、掉电恢复、串口波特率和丢包情况。

### 阶段 3：协议复用

- 在 BLE 链路上承载现有 `gp_led_matrix_protocol`。
- 先支持 `Ping`、`Heartbeat`、`SetBrightness`、`SetMode`。
- 再支持 `SetAction`。

### 阶段 4：业务联调

- 打通语音颜色、预设图案、调试菜单控制。
- 打通状态摘要和最近命令显示。
- 验证断链恢复和异常状态提示。

## 11. 风险与对策

### 风险 1：BLE 模块透明传输行为不可控

对策：

- 在选型阶段先做最小原型验证。
- 明确 GATT 服务、通知缓存和 MTU 约束。

### 风险 2：AI8051U UART 接收压力上升

对策：

- 采用环形缓冲区。
- 必要时加入串口 DMA 或定时器辅助收包。
- 保留轻量级包头校验和超时清包机制。

### 风险 3：BLE 延迟导致显示控制体验变差

对策：

- 优先传输短控制包。
- 大图或连续帧功能延后。
- 在 ESP32 UI 中明确显示链路在线状态和最近一次 ACK 时间。

### 风险 4：电源和射频干扰影响稳定性

对策：

- BLE 模块与 LED 电源地线布局分离。
- 预留去耦和电源滤波。
- 在 WS2812 高负载场景下单独测试通信稳定性。

## 12. 建议交付物

`BT_Version` 分支建议逐步形成以下交付物：

- BLE 替代 I2C 的总体设计文档。
- ESP32 侧 BLE transport 抽象层。
- AI8051U 侧 UART 接入版本协议解析前端。
- 最小收发联调日志。
- 断链恢复和 ACK 策略验证记录。

## 13. 结论

推荐路线不是“在 AI8051U 上直接实现蓝牙协议栈”，而是：

- ESP32-S3 负责 BLE 主连接和 GATT 数据管理。
- AI8051U 继续专注协议解析和 WS2812 执行。
- 通过外挂 BLE 透明串口模块把 I2C 物理链路替换为 BLE + UART 组合。

这样可以最大限度复用当前 I2C 版本已经稳定的协议和业务逻辑，同时把蓝牙迁移的复杂度控制在传输层和硬件适配层。
