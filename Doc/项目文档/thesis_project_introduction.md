# 毕业论文项目介绍

## 1. 项目概述

本项目面向“语音交互驱动的 LED 点阵显示系统”这一应用目标，构建了一个由 `AI端`、`LED端` 和联调工具链组成的双控制器协同系统。

系统整体分为两级：

1. `AI端` 以 ESP32-S3 为核心，负责语音交互、意图识别、动作对象生成、链路状态管理以及上位调试显示。
2. `LED端` 以 STC AI8051U 为核心，负责接收显示控制协议、解析动作命令、执行 WS2812 点阵扫描刷新，并通过 USB 调试链路输出运行状态。

在当前版本中，两端通过 `HC-05` 蓝牙串口透明传输模块建立无线通信链路，形成“语音输入 -> 动作生成 -> 蓝牙传输 -> 协议执行 -> 点阵显示”的完整闭环。

## 2. 总体结构

项目仓库主要由以下几部分组成：

### 2.1 AI端工程

- 路径：`External/xiaozhi-esp32/`
- 基础框架：基于 ESP-IDF 的小智语音交互工程
- 当前作用：承载语音交互主流程、板级初始化、自定义矩阵控制扩展和蓝牙传输逻辑

AI端内部又可以细分为以下模块：

- `main/boards/lichuang-dev/`
  - 负责板级初始化、HC-05 配置、串口资源接入和系统状态协调。
- `GP_Port/gp_led_matrix_esp32.h/.cc`
  - 负责把语音结果或调试命令映射为统一的矩阵动作对象。
- `GP_Port/transport/`
  - 负责自定义矩阵协议的发送、回包校验、链路状态维护和错误处理。
- `GP_Port/ui/`
  - 负责调试界面、链路状态显示、最近命令摘要等可视化反馈。

### 2.2 LED端工程

- 路径：`STC51/Project/ws2812_driver/`
- 基础框架：基于 STC AI8051U 的 WS2812 驱动工程
- 当前作用：承载协议接收、动作执行、点阵扫描刷新和 USB 调试输出

LED端内部主要包含以下层次：

- `Sources/app/`
  - 负责应用层流程调度和测试模式入口。
- `Sources/mid/`
  - 负责图像渲染、动画步进和显示中间逻辑。
- `Sources/drv/`
  - 负责 WS2812 驱动、74HC595 行选驱动、蓝牙调试桥等底层外设实现。
- `Sources/inc/`
  - 负责配置头文件、接口声明和共享常量定义。

### 2.3 文档与联调工具

- `Doc/项目文档/`
  - 用于记录系统架构、协议设计、问题追踪和阶段性总结。
- `.github/prompts/`
  - 用于维护开发过程中的阶段任务和协作约束。
- `tools/ws2812_dev_cycle.py`
  - 负责自动构建、下载、打开监视窗口和串口联调，是当前版本的主联调脚本。

## 3. 功能实现方案

## 3.1 AI端功能实现

AI端的核心职责是把高层语义转换为可执行的矩阵动作命令，并通过无线链路可靠发送给 LED 端。

### 3.1.1 语音结果到动作对象的映射

AI端在保留小智原有语音交互能力的基础上，新增了自定义矩阵控制扩展。其基本处理流程如下：

1. 语音识别模块输出颜色、图案或状态类结果。
2. `gp_led_matrix_esp32` 模块将结果转换为统一动作对象。
3. 动作对象被编码为自定义矩阵协议帧。
4. 协议帧通过蓝牙传输层发送给 LED 端。

这种分层方式使语音理解逻辑与 LED 硬件执行逻辑解耦，便于后续继续扩展颜色、动画、字幕等更多指令类型。

### 3.1.2 蓝牙传输链路

AI端通过外接 `HC-05` 模块与 LED 端建立透明串口通信。当前版本中，AI端蓝牙模块使用 `UART1(GPIO10/GPIO11)` 接入，链路工作流程如下：

1. 系统上电后，AI端先以 `38400` 波特率进入 HC-05 AT 配置模式。
2. AI端依次执行“设置命令 -> 对应查询命令”的成对流程。
3. AI端设置主机角色、设备名、PIN 码、连接模式和固定从机绑定地址。
4. 所有配置完成后发送 `AT+RESET`。
5. 收到 `OK` 后，AI端本地串口切换到 `115200` 数据波特率。

当前版本中，AI端使用固定地址绑定方式与 LED 端蓝牙模块建立关系，避免了运行时扫描、配对和动态寻址带来的复杂性，提升了系统启动阶段的确定性。

### 3.1.3 调试界面与状态反馈

AI端还实现了调试界面扩展，用于显示以下信息：

- 蓝牙链路连接状态
- 最近一次下发命令摘要
- 协议回包结果
- 错误信息与异常提示

该界面为联调阶段提供了直观的运行反馈，便于快速定位链路异常、参数不一致或命令执行失败等问题。

## 3.2 LED端功能实现

LED端的核心职责是接收 AI 端下发的协议命令，并将其转换为对 WS2812 点阵的具体控制操作。

### 3.2.1 协议接收与串口桥接

LED端通过 `UART2(P4.2/P4.3)` 接入 HC-05 模块。相关接收与调试逻辑集中在 `gp_led_matrix_bt_debug.c` 中，主要功能包括：

- 上电时自动完成 HC-05 从机侧配置
- 将蓝牙串口输入转交给协议解析路径
- 把关键日志经 USB 调试口输出到上位机
- 支持发送 AT 指令与查询结果的监视

当前版本中，LED端同样遵循“设置命令 -> 查询命令 -> 全部完成后 RESET -> 收到 OK 后切换本地波特率”的严格流程，从而保证两端蓝牙参数一致。

### 3.2.2 协议解析与动作执行

LED端接收到数据后，会按照自定义矩阵协议进行解析，并根据命令类型调用对应执行路径。当前已实现的能力包括：

- 状态显示命令
- 错误显示命令
- 固定预设图案显示
- 帧数据更新与图像刷新
- 协议回包与执行结果反馈

在结构设计上，协议解析层只负责解释命令含义，而具体显示执行则交由原有 WS2812 驱动与渲染层完成，从而复用了既有的稳定扫描链路。

### 3.2.3 WS2812 点阵驱动

LED端采用 `WS2812 + 74HC595 + PMOS` 的复用扫描方案，底层已经完成以下关键实现：

- 基于 PWM + DMA 的数据发送路径
- 基于 74HC595 的行选控制
- 基于定时器的扫描节拍调度
- 复位尾波和行间隔安全控制

该驱动结构兼顾了资源受限单片机平台上的刷新效率与显示稳定性，为上层协议控制提供了可靠执行基础。

## 3.3 自定义通信协议实现

为了在 AI 端与 LED 端之间传递高层动作命令，项目实现了自定义矩阵控制协议。该协议的设计目标包括：

- 支持不同类型动作对象的统一编码
- 支持回包确认与错误反馈
- 便于在后续继续扩展更多显示效果
- 避免 AI 端直接依赖 LED 端底层硬件细节

当前协议已经支持命令下发、状态回包和调试日志配合验证。AI 端通过传输层维护发送状态，LED 端在执行后返回结果，从而构成基本的可靠交互机制。

## 4. 联调工具与开发流程

为提高双端协同开发效率，项目新增了 `tools/ws2812_dev_cycle.py` 作为主联调脚本。该脚本实现了以下自动化流程：

1. 调用 ESP-IDF 构建并下载 AI 端固件。
2. 打开 AI 端监视窗口。
3. 调用 Keil CLI 重新构建 LED 端固件。
4. 重新打开 AI8051U 串口监视窗口。
5. 可选自动发送蓝牙调试命令序列。

与早期 PowerShell 方案相比，Python 脚本在串口管理、跨工具调用和后续维护方面更稳定，也更适合作为论文中的工程化支撑内容。

## 5. 当前系统特性

截至当前版本，系统已具备以下特性：

- 完成 AI 端到 LED 端的无线蓝牙控制链路搭建。
- 完成 HC-05 主从参数自动配置与固定地址绑定。
- 完成语音结果到矩阵动作对象的映射通路。
- 完成 LED 端协议接收、执行和回包反馈。
- 完成 WS2812 点阵稳定刷新与调试日志输出。
- 完成 AI 端界面化链路状态显示和联调脚本自动化。

这些功能共同构成了一个可演示、可调试、可继续扩展的嵌入式智能显示系统原型。

## 6. 项目意义

本项目的意义不仅在于实现语音控制 LED 点阵显示，更在于完成了一个跨平台、分层明确、具备工程化特征的双控制器协同系统。其主要价值体现在以下几个方面：

1. 验证了语音交互系统与资源受限单片机显示系统之间的协同方式。
2. 验证了通过自定义协议实现“高层语义控制”和“底层硬件执行”解耦的可行性。
3. 建立了从系统设计、协议实现、驱动适配到联调工具链的一体化工程路径。
4. 为后续扩展字幕显示、更多动画模式和更复杂交互逻辑提供了结构基础。

## 7. 后续可扩展方向

在当前实现基础上，系统后续仍可沿以下方向继续完善：

- 增加自由文本字幕显示能力
- 完善心跳超时与自动恢复机制
- 扩展更多显示动作与动画效果
- 进一步优化无线链路稳定性和异常恢复流程
- 补充更完整的实机联调记录与性能测试数据

从论文撰写角度看，当前版本已经具备较完整的系统架构、关键模块实现和工程验证基础，可作为毕业设计主体实现进行描述。
