# 软件结构与实现逻辑论文补写总稿

## 1. 软件系统总体架构

本课题的软件系统围绕“`AI端` 生成显示意图并通过蓝牙驱动 `LED端` 执行显示”这一核心目标展开。结合当前仓库结构，可以将整个软件系统划分为 4 个相互配合的组成部分：

1. `LED端显示驱动`：负责点阵图像缓存、行扫描刷新以及 PWM + DMA 波形输出。
2. `AI端接口调度`：负责本地调试、图像结果编排、蓝牙发包、ACK 处理和本地预览。
3. `蓝牙通信协议`：负责定义两端共享的数据格式、命令事务和回复语义。
4. `本地绘图脚本`：负责在主机侧将 prompt、文本、动画和 Python 绘图语句转换为统一矩阵结果，并通过 HTTP/WebSocket 送达 `AI端`。

如果从端到端工作流观察，上述 4 部分形成了一条清晰的软件主链路：

```text
主机侧绘图请求 / AI端本地触摸输入
            -> AI端接口调度与预览缓冲
            -> 蓝牙通信协议封装
            -> LED端动作执行与图像缓存
            -> PWM + DMA 输出到 16x16 WS2812 点阵
```

这种分层结构的核心优点在于：每个部分都围绕单一职责展开，同时又通过共享协议和清晰的接口边界保证了整体协同。换言之，系统不是由若干彼此耦合的脚本和驱动拼凑而成，而是由“主机生成层、调度控制层、协议层、驱动执行层”四个层次稳定衔接而成。

## 2. LED端显示驱动

`LED端` 软件运行在 AI8051U/STC51 平台上，主要负责把上层提供的图像内容转化为 WS2812 芯片能够识别的精确定时波形。其内部又可分为 6 个逻辑层次：硬件波形驱动层、帧缓存与编码层、图像渲染层、动作与显示控制层、通信接入层以及调度与运行时组织层。

在最底层，系统并不采用纯软件 bit-bang 方式逐位拉高拉低数据线，而是先把每一位颜色数据编码为 PWM 比较值，再通过 PWMAT-DMA 自动搬运到 PWM 比较寄存器中。这样，CPU 只需要完成缓存准备和 DMA 触发，真正的高精度波形输出由硬件外设保证。为了降低编码开销，驱动还建立了 `256 x 8` 的位展开查找表，将一个字节直接映射为 8 个 PWM 占空比值，从而避免在刷新过程中频繁逐位判断。

在显示组织上，`LED端` 采用“双通道输出 + 行选扫描”的结构。也就是说，底层并不是一次性驱动 256 个像素，而是利用 2 路 PWM 数据线和 74HC595 行选芯片，对 16x16 点阵执行成对行扫描。对于每一组待刷新的两行，系统先从像素缓存中读出 GRB 顺序颜色值，再将其编码为行级 PWM 序列，随后交织为双通道 DMA 数据，最后通过行选切换和 PWMAT-DMA 输出完成一次刷新步进。这一过程持续重复，从而实现整屏稳定显示。

在显示策略上，`LED端` 并不是简单地区分“在线”与“离线”，而是进一步区分“链路在线”与“远程接管显示”。所谓链路在线，表示 `AI端` 与 `LED端` 仍然能够继续收发协议包；所谓远程接管显示，则表示当前画面确实由远程动作、远程单帧或远程动画占有。这一区分非常重要，因为即使蓝牙链路依然在线，只要远程侧没有持续接管显示，本地离线图案和本地按键逻辑仍然应当可以继续工作。

因此，`LED端` 在整个系统中的作用可以概括为：接收上游定义好的动作和图像数据，负责缓存组织、显示控制权判定以及精确定时波形输出，是软件系统中距离实际硬件显示最近的一层。

## 3. AI端接口调度

`AI端` 软件运行在 ESP32 平台上，它的核心职责不是直接产生 PWM 波形，而是作为整个系统的软件中枢，负责把本地调试结果、主机侧绘图结果和设备运行状态组织成可以稳定下发到 `LED端` 的协议事务。

从结构上看，`AI端` 至少包含 5 个关键组成部分。首先是板级接入层，它在 `lichuang_dev_board.cc` 中负责初始化触摸屏、显示屏、网络、蓝牙模块以及矩阵控制器。其次是本地调试交互层，它通过 `GpDebugLcdDisplay` 提供调试菜单、颜色点、矩阵预览和链路状态面板，并将触摸输入转化为结构化状态对象。再次是矩阵编排层，也就是 `GpLedMatrixEsp32`，它负责将动作对象、RGB332 整帧、紧凑位图单帧和动画批次统一转换为共享蓝牙协议包。其下方是蓝牙传输层，它通过 `GpMatrixBtUartTransport` 持续完成 UART 收发和整包重组。除此之外，板级层还实现了本地 HTTP 预览接口和 Debug WebSocket 通道，用来接收主机侧生成的图像结果并先在 LCD 上预览，再决定是否继续向 `LED端` 转发。

在运行逻辑上，`AI端` 启动后会先配置 HC-05 模块，包括角色、名称、PIN 码、绑定地址和数据传输波特率。随后板级代码创建 `GpLedMatrixEsp32` 对象，并将其与本地调试界面连接起来。对于本地触摸输入，`AI端` 并不会直接写串口，而是先通过回调把调试状态投入后台命令队列，再由后台任务统一调用矩阵控制器执行发送。对于主机侧通过 Debug WebSocket 送来的 `matrix_pattern_result` 或动画消息，`AI端` 则先在本地 LCD 上更新矩阵预览，再把结果转交给蓝牙协议发送层。

`AI端` 的另一个关键价值在于 ACK 处理。所有命令最终都会经由 `SendCommand()` 打包，自动分配 `sequence`，计算 `header_crc8` 与 `packet_crc16`，并在需要时进入 `ReadReply()` 轮询匹配回复包。只有当 `packet_type=Reply`、`reply_to_sequence`、`command` 和 CRC 都匹配成功时，这次事务才被视为真正完成。由此可见，`AI端` 并不是“把字节发出去就算完成”，而是承担了链路确认与错误反馈的职责。

因此，在整个毕业设计的软件系统中，`AI端` 的角色应被理解为“显示语义调度层”。它上接主机服务和人机交互，下接蓝牙协议和 `LED端` 驱动执行层，是连接各软件部分的核心枢纽。

## 4. 蓝牙通信协议

为了让 `AI端`、`LED端` 与主机侧绘图桥围绕同一套数据契约协同工作，本课题设计了一套轻量二进制蓝牙通信协议。该协议并不依赖复杂的上层网络库，而是针对 HC-05 + UART 场景做了定制化裁剪。

在结构上，每个协议包均由固定长度包头、可变长度负载和两字节尾部 CRC 组成。包头中同时包含魔数、版本号、头长度、包类型、标志位、序号、回复序号、负载长度、命令字和头部 CRC8。整包末尾再附加 CRC16，对 `header + payload` 进行完整性校验。这样的双层校验机制使得接收侧能够先快速判断“包头是否合法”，再决定是否信任负载长度并继续收包，从而显著降低串口噪声导致的误判风险。

在事务语义上，协议采用统一的 `Request/Reply` 机制。Reply 不使用独立命令字，而是直接回显原命令，并通过 `reply_to_sequence` 关联到原请求的 `sequence`。这样，任何命令都可以复用同一套 ACK 匹配规则。协议中目前定义的核心业务包括：亮度设置、模式切换、动作对象下发、RGB332 整帧传输、滚动字模传输、动画批次传输以及调试 LED 控制等。

其中，完整 RGB332 帧采用 `FrameStart + FrameChunk + FrameCommit` 三阶段事务。一帧 16x16 RGB332 图像总长度为 256 字节，在最大分片大小 64 字节约束下，需要拆分为 4 个显式偏移分片。相比之下，主机侧与 `AI端` 之间更常使用一种紧凑位图格式，即 16 行 1-bit 位图加前景/背景 RGB888，共 38 字节。这种格式在保持显示语义不变的同时，大幅降低了蓝牙传输量，因此非常适合主机绘图和快速预览场景。动画批次则进一步建立在紧凑位图格式上，统一由 `AnimationStart + AnimationFrame x N + AnimationEnd` 构成，最大帧数为 24，帧间隔采用 `1..65535 ms` 的共享字段表示。

从软件工程角度看，这套协议最大的价值在于把多端协同统一到同一语言之下。`AI端` 按同一规则构包，传输层按同一规则验包，`LED端` 按同一规则接收和回包，而主机侧绘图桥又根据这套规则生成紧凑位图与动画对象。因此，协议并不只是“蓝牙传输格式”，而是整个系统的软件公共接口。

## 5. 本地绘图脚本与联调支撑

为了让上层绘图与论文展示更加直观，本课题在主机侧构建了一套本地绘图桥和联调工具链。其目标不是直接替代嵌入式端的功能，而是在主机与设备之间增加一个对人类和 LLM 都更加友好的中间层。

主机侧桥接服务的核心文件是 `gp_mcp_endpoint_client.py`。它同时扮演 MCP 客户端、本地工具服务端、Debug WebSocket 服务端和 HTTP 控制服务端 4 个角色。一方面，它可以接收远端 `tools/call` 请求，执行本地绘图逻辑；另一方面，它又能通过 HTTP 或 WebSocket 把生成结果送到 `AI端`。这种设计意味着主机侧并不是简单输出一个图片文件，而是可以直接参与系统的调试和控制闭环。

在数据生成上，主机侧定义了统一的 `matrix_frame_v1` 和 `matrix_frame_sequence_v1` 两类结果对象。前者用于描述单帧，包括 `frame_rgb332_hex`、`bitmap_rows_hex`、前景色、背景色和尺寸信息；后者用于描述文本或动画序列，包括帧列表、帧数和帧间隔等。对于最常见的位图输入，桥接服务还实现了归一化逻辑，既支持标准的 64 个十六进制字符写法，也兼容 16 行 16-bit token 形式，并最终统一还原为标准输出格式。

在工具实现上，主机侧至少提供了 4 类能力。第一类是 prompt 模板渲染，它通过颜色关键词识别和图案模板匹配快速生成 16x16 图案。第二类是受限 Python 绘图，它在 Pillow 1-bit 画布上执行经过 AST 白名单过滤的简化绘图语句，以兼顾灵活性和安全性。第三类是文本渲染，它将每个字符转为一个 16x16 位图帧，形成逐字序列。第四类是动画序列渲染，它允许输入多帧位图或逐帧绘图定义，并在帧数超出 `LED端` 缓冲能力时自动重采样与调整节拍。

在结果投递上，主机侧优先通过 Debug WebSocket 把结构化矩阵结果直接推送给 `AI端`。如果当前 WebSocket 不可用，则退化为 HTTP 预览回退路径，即先把矩阵帧转换为一张本地 PNG 预览图，再请求 `AI端` 主动拉取显示。这种双路径设计保证了系统在不同调试阶段都具备较高的可用性。

此外，`ws2812_auto_debug.py` 将 `LED端` Keil rebuild、STC 串口监视以及 `AI端` 的 ESP-IDF build/flash/monitor 串接为一次统一操作。这样，开发者不需要分别操作多个终端和工具，即可完成双端软件的构建与联调准备。这一自动化流程显著降低了跨平台嵌入式联调的复杂度。

## 6. 端到端工作流程分析

为了更清晰地展示四类软件之间的协同关系，下面分别给出 3 条典型工作流程。

### 6.1 本地触摸调试流程

当用户在 `AI端` LCD 调试界面上调整颜色、效果或图案时，本地界面首先生成一个 `GpColorDebugState` 对象。该对象通过回调进入后台调试命令队列，再由 `GpLedMatrixEsp32` 将其压缩为 `GpMatrixActionPayload`。随后 `AI端` 构造 `SetAction` 请求包，通过 HC-05 下发给 `LED端`。`LED端` 在接收并校验后，由动作控制层更新当前显示状态，最终由 PWM + DMA 刷新链路完成实际显示。若 `LED端` 返回 ACK，则 `AI端` 再把链路状态反馈到本地调试界面。整个流程体现的是“本地人机交互 -> 动作对象 -> 协议请求 -> 硬件显示”的控制链。

### 6.2 主机图案绘制流程

当主机通过 `/control/matrix_prompt_16x16` 提交“绘制一个青色爱心”之类的请求时，桥接服务会先将自然语言映射为图案模板和颜色参数，再生成统一的 `matrix_frame_v1` 结果对象。如果 Debug WebSocket 可用，该结果会直接以 `matrix_pattern_result` 消息推送到 `AI端`；否则桥接服务先生成 PNG 预览图，并通过 HTTP 回退路径请求 `AI端` 拉取。`AI端` 在接收到结果后，先在本地 LCD 预览，再把紧凑位图负载转发为蓝牙协议事务，最终由 `LED端` 显示出来。这条流程体现的是“主机绘图 -> AI 端预览缓冲 -> 协议转发 -> LED 显示”的协同链。

### 6.3 动画批次播放流程

当主机需要播放一个多帧动画时，桥接服务会先把输入序列归一化为最多 24 帧，并根据重采样结果修正 `frame_interval_ms`。随后它通过 Debug WebSocket 依次向 `AI端` 发送 `matrix_animation_start`、多条带 `frame_index` 的 `matrix_pattern_result` 以及 `matrix_animation_end`。`AI端` 在收到这些消息后，先将各帧缓存到本地动画暂存区并循环预览；当确认整组动画已经接收完整后，再统一调用 `ShowBitmapAnimation()` 把整批动画作为协议事务下发给 `LED端`。`LED端` 将这批帧缓存到本地动画缓冲区后，按照给定帧间隔循环播放。与单帧显示相比，这条流程增加了一个明显的“AI 端缓存批处理”阶段，从而避免了逐帧蓝牙直播导致的节拍抖动问题。

## 7. 软件设计特点分析

结合前述结构和流程，可以将本课题的软件设计特点概括为以下几点。

第一，系统具有明确的分层结构。主机绘图、`AI端` 调度、协议定义与 `LED端` 驱动彼此职责清晰，降低了后期维护成本。第二，系统强调链路可靠性。无论是协议层的双重 CRC、ACK 匹配，还是传输层的整包重组和超时处理，都是围绕“不让错误字节静默进入显示结果”这一目标设计的。第三，系统具备较好的扩展性。动作对象、紧凑位图和动画批次的引入，使得在不改动底层 PWM + DMA 驱动的前提下，可以持续扩展上层显示语义。第四，系统具有较强的可调试性。本地 LCD 预览、Debug WebSocket、HTTP 预览接口、截图上传以及自动化联调脚本共同构成了一套完整的观测链路，使软件行为不仅“能运行”，而且“能被观察、能被复现、能被验证”。

## 8. 本章小结

综上所述，本课题的软件系统并不是单一的显示驱动程序，而是一套覆盖主机服务、嵌入式调度、蓝牙协议和底层显示执行的完整软件体系。其中，主机侧负责将高层输入转化为统一图形对象，`AI端` 负责完成调度、预览和蓝牙事务控制，协议层负责提供跨设备一致的数据契约，`LED端` 则负责把最终结果落实为稳定的点阵显示。四类软件部分既各自独立，又通过清晰的接口衔接成一条完整闭环，这也是本课题能够同时兼顾功能实现、系统可扩展性和工程可调试性的根本原因。
